# Agent instructions

Everything here is internal to this repository. No manifest publishes these files, and the APM package doesn't carry them. The only references from elsewhere in the tree are documentation naming the directory and the `generated_by` provenance string that `skill-tokens.sh` writes into each `tokens.json`. That makes this the opposite of [`../scripts/`](../scripts/AGENTS.md), whose every filename is a published entry point, so a rename here costs a grep across this repository and nothing more.

Reach for this directory when a gate needs a program rather than a task body, or when a question about this repository's own toolchain needs one. Reach for `scripts/` only when consumers run the thing themselves.

These back the lint and build gates. `check-script-hygiene.sh` refuses a script whose output an operator's configuration could reshape, and it defines the rules that stay text-matched while `.ast-grep/rules/` defines the structural ones. `skill-tokens.sh` measures what each skill costs in context and writes `tokens.json` beside each `SKILL.md`. It asks git for its file list rather than walking the filesystem, because a walk also finds build artifacts, and sending a compiled `.pyc` to the token counter writes a negative count into a file nothing gates on. `skill-limits.sh` checks each skill against the platform's name and description limits. `check-versions.sh` holds the six published version literals to the latest release tag, standing witness over the `cog.toml` hooks that rewrite them during a bump. `lint-draft.sh`, `test-guards.sh`, `fuzz.sh`, and `go-ldflags.sh` serve their matching tasks, and `mise-bootstrap` is the committed shim that runs the pinned mise where PATH has none.

`release-readiness.sh`, `release-dispatch.sh`, and `release-verify.sh` back the three release tasks, described under Releases in [`../AGENTS.md`](../AGENTS.md). Only the dispatcher has an effect, and it's the thinnest of the three on purpose. None of them fixes anything, which is what lets a caller run one to ask a question rather than to act.

`skill_attribution.py` answers to nothing. It reports which tool calls each skill made, reading the `attributionSkill` field Claude Code stamps on every assistant record in a transcript, and it exists so this repository can judge a preflight script on what its agents stopped doing rather than on the argument for adding it. A forked skill's calls are exact, since its subagent transcript bounds the run. An in-context skill's are an upper bound, because attribution names the last skill loaded and holds until another displaces it. Nothing runs this on a schedule, and no task wraps it.

`--timing` reads those same runs on the clock, reporting how long each takes with the operator's share taken out. A turn that ends and waits for someone to type, and an `AskUserQuestion` waiting on its answer, are both visible in the records and both subtracted. Only a permission prompt sits outside both, since it suspends a tool call without writing a record of its own, so it remains in the active figure looking like a slow command. Read a per-skill active figure as work plus whatever approvals it sat through.

Tests live in [`../tests/tools/`](../tests/tools/), mirroring this directory. `mise run test-py` runs the Python suites and `mise run test-hooks` runs the bats ones, walking `../tests/` in full, so a new suite has only to live in the mirror. `fix_prose_replacements.py`, `check-versions.sh`, `release-verify.sh`, `release-dispatch.sh`, `skill_attribution.py`, and `release-readiness.sh` have suites today. Each drives its subject as a subprocess, because the command line and the exit code are the contract worth asserting rather than the functions behind them. A stub `vale` on PATH backs the first. The second runs against a throwaway repository containing the same six version sites, and the third against a throwaway repository holding a deliberately lightweight tag. A stub `gh` recording its arguments backs the fourth, and a synthetic projects directory the fifth. The sixth runs against a throwaway repository with a bare origin beside it, with `gh`, `mise`, and `cog` all stubbed to answer the same way every time, so the comparison of `HEAD` against origin's release branch is the only thing any assertion turns on. That comparison is the check the suite exists for: it replaced a branch-name test that failed in every agent worktree, and the cases it holds are a worktree branch and a detached `HEAD` sitting on the released commit. The suites stop at two boundaries on purpose. Nothing fabricates a signed tag, since that would mean holding the release signing key, so no fixture covers the signed path and running `verify-devtools-release` against a real tag is what exercises it. And no test dispatches a workflow, since finding out that way costs a release. A new program here should arrive with a suite beside it under that mirror.

A Python program here is a standalone uv script: a `#!/usr/bin/env -S uv run --script` shebang, plus the inline metadata block from Python Enhancement Proposal 723 pinning `requires-python`. Keep them dependency-free while they can be. Shared logic that outgrows one file goes to a sibling module first, and to a published `devtools-common` package only once something outside this repository needs it, since a deployed skill script can't import from `packages/` and this project builds no wheel.

Don't write a shell script whose body is another language behind a shell wrapper. It happened twice here, and no gate caught either one. The code scanning workflow flagged a script under `packages/agents/*/.apm/` because it scans the APM package. The scan never looks in this directory, so it missed the twin here.
